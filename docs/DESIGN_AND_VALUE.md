# Northstar design and value review

## Product thesis

Northstar is worthwhile if it remains the coordination layer between product intent and execution evidence. Its job is to answer five questions reliably:

1. What work matters next?
2. Why does it matter?
3. Who owns it, on which branch, and where is execution authoritative?
4. Which plan or context should the next teammate or assistant read?
5. What changed, who handed it off, and were all trackers updated?

Issues, project boards, specifications, implementation methods, and knowledge graphs answer adjacent questions. Northstar links them without trying to replace them.

## Responsibility model

| Layer | Owns | Does not own |
|---|---|---|
| Northstar | Portfolio order, story, priority, lifecycle, owner lock, branch, tracker links, handoff and sync audit | Detailed implementation planning, code, review, capacity planning |
| GitHub/GitLab | Execution discussion, assignees, issues, PRs/MRs, service-visible history | Cross-service source of truth |
| Wayfinder | Discovery for a large or uncertain item | Portfolio priority or delivery closeout |
| Spec Kit | Formal feature specification and acceptance boundary | Portfolio ownership or tracker reconciliation |
| cc-rpi | Research → Plan → Implement → Validate execution method | Roadmap, item lock, or cross-service audit |
| Graphify | Optional persistent codebase and architecture context | Work lifecycle or delivery authority |

## Why the split matters

`Plan kind` and `Execution method` are separate axes:

| Planning route | Execution method | Example |
|---|---|---|
| Direct | Native | Small, clear change implemented from the item brief |
| Direct | RPI | Clear outcome that still benefits from disciplined research and validation |
| Wayfinder | Native or RPI | Technically foggy initiative clarified before implementation |
| Spec Kit | Native or RPI | Product feature specified formally before implementation |

This avoids turning every optional companion into a competing lifecycle.

## Best-practice assessment

Northstar follows the core conventions of a maintainable agent skill:

- The trigger descriptions say what each skill does and when to use it.
- Primary `SKILL.md` files remain below 100 lines.
- Detailed contracts and examples are split into one-level references.
- Deterministic validation, atomic writes, locking, journaling, and synchronization live in a reusable standard-library engine instead of being regenerated by the model.
- Natural language is the user interface; internal commands are documented for agents, CI, and troubleshooting.
- Credentials are never persisted, and external mutations require explicit setup and preview gates.
- Optional companions are detected and attributed without being installed silently.

## Risks and mitigations

| Risk | Current mitigation | Remaining work |
|---|---|---|
| Two teammates claim the same item from different clones | Install the serialized claim workflow on one `Home`; default-branch merge remains authoritative | A dedicated service would be needed for multi-repository transactions |
| GitHub succeeds and GitLab fails | Durable outbox, targeted retry, scheduled reconciliation, and opt-in live contracts | Providers still cannot participate in one atomic transaction |
| Markdown table becomes unwieldy | Active-item threshold, archival policy, generated views and dashboard | Very large portfolios still need a dedicated planning system |
| Companion behavior drifts | Compatibility manifest, detection, explicit profiles and boundaries | Add pins only for demonstrated incompatibilities |
| Audit evidence is incomplete | Mandatory evidence, policy CI, protected Git history, and SHA-256-linked audit records | Signed commits remain an optional organization policy |

## Verdict

Northstar makes sense for small and medium engineering teams that want repository-owned product context and auditable handoffs across assistants and trackers. It should not be marketed as a replacement for Jira, Linear, GitHub Projects, GitLab planning, Spec Kit, or cc-rpi. Its durable niche is the connective tissue between them.

The repository includes baselines for the operational controls above. Teams must still install the workflow templates, configure protected branches and sandbox credentials, and choose retention/notification policies appropriate to their environment.
